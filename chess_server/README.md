# Chess server setup

## Run locally from VS Code

Open the `ChessMultiplayer` project folder in VS Code, install the Python
extension, select an interpreter with the dependencies from both
`chess_server/requirements.txt` and `chess_client/requirements.txt`, then press
**F5** and choose **Chess: Run Full Game**. VS Code starts the Master Server,
Game Node, and desktop client in separate integrated terminals; no manual
`cd` commands are needed. Stop the compound session to stop all three.

The launch profile uses `local-development-only` as the shared internal token
for local match-history submissions. It is a public development value: replace
it with the same private `CHESS_INTERNAL_SERVER_TOKEN` on both servers before
any network deployment. Cloudinary uploads also require `CLOUDINARY_API_KEY` and
`CLOUDINARY_API_SECRET` in the Master Server's environment. The Master launch
profile reads these from the ignored workspace `.env` file; enter them there,
never in `launch.json` or source control. The Firebase service account file
must be available to the Master Server as described below.
Both server scripts also load the workspace `.env` when run directly, so the
Game Node and Master use the same local match-save token.

## Firebase match history

The Master Server uses Firebase Admin credentials to authenticate players and
write match history to Cloud Firestore. Enable Firestore in the Firebase
project and provide a service-account JSON file outside source control. The
service account needs permission to read and write Firestore documents.

Set `FIREBASE_SERVICE_ACCOUNT` to the file path on the Master Server. If it is
not set, the server looks for `firebase_service_acc.json` beside
`auth_verify.py`. The local VS Code launch profile uses this default path;
keep the service-account file private and out of source control.

Completed matches are stored at:

```text
users/{uid}/matches/{match_id}
```

Each match document contains the mode, result, players and teams, start and
completion times, starting and final FEN, termination reason, and the full
ordered UCI/SAN move list. The same match document is written under every
participant's user profile. The lobby loads the authenticated player's recent
matches; players can inspect or share a match record in lobby chat.

Chat history is stored in the `lobby_chats` collection. Messages linked to a
match are also copied to each participant's
`users/{uid}/matches/{match_id}/chat/{message_id}` subcollection. Sharing a
match stores its full move record once in `shared_matches/{match_id}`; chat
messages keep a compact summary and match ID, so lobby history does not repeat
the entire move list. The lobby loads recent chat messages on entry, and the
profile can show a match's saved chat. Messages sent from the in-game chat,
including Cloudinary attachment metadata, are saved to the same per-match chat
subcollection for every participant.

## Cloudinary uploads

The client uploads media directly to Cloudinary using short-lived signed
parameters generated by the authenticated Master Server. The API secret stays
on the Master Server and is never sent to clients. Set these environment
variables there:

| Variable | Description |
| --- | --- |
| `CLOUDINARY_CLOUD_NAME` | Cloud name; defaults to `dyfmgr6vl` |
| `CLOUDINARY_API_KEY` | Cloudinary API key |
| `CLOUDINARY_API_SECRET` | Private Cloudinary API secret |
| `CLOUDINARY_UPLOAD_PRESET` | A **signed** upload preset |

Configure the preset as signed, allow only `jpg`, `jpeg`, `png`, `gif`,
`webp`, `mp4`, `mov`, `webm`, `wav`, `mp3`, `m4a`, `ogg`, `pdf`, `doc`, and
`docx`, and set the preset's maximum file size to 25 MB. The application also
checks file type and size before sending a chat attachment. The Master rate
limits upload signatures to three per user per minute.

The chat stores attachment metadata and the Cloudinary secure URL in Firestore;
the file itself remains in Cloudinary. Images, videos, documents, and recorded
voice notes share the same upload path. The in-game chat also has a file button;
it uses the same signed-upload flow and sends the resulting attachment to the
other players in the match.

## In-game voice/video calls

During a running game, choose **Gọi thoại / video**, select one player, and
wait for them to accept. A 1vs1 room calls its opponent; in 2vs2, either team
can invite any one player in the room. The call window shows the local and
remote video tiles. Microphone and camera are off by default and have separate
on/off controls. Camera video is sent as small JPEG frames over the Game Node's
UDP media port; TCP is used only for call invitations and status. Install the
client requirements to enable webcam capture (`opencv-python`).

## Server connection settings

Set the same private `CHESS_INTERNAL_SERVER_TOKEN` on the Master Server and
every Game Node. It is used to sign match-history submissions; do not put it in
client configuration or commit it to source control.

Configure these environment variables before starting each process:

| Variable | Process | Default |
| --- | --- | --- |
| `MASTER_SERVER_HOST` | Game Node | `127.0.0.1` |
| `MASTER_TCP_PORT` | Master and Game Node | `8000` |
| `MASTER_UDP_PORT` | Master and Game Node | `9000` |
| `GAME_TCP_PORT` | Game Node | `8001` |
| `GAME_UDP_PORT` | Game Node | `8002` |
| `CHESS_SERVER_HOST` | Client | `127.0.0.1` |
| `CHESS_SERVER_PORT` | Client | `8000` |

Allow the Master TCP/UDP ports and Game Node TCP/UDP ports through the
deployment firewall. The Game Node must be able to reach the Master TCP port
to persist completed matches. In particular, allow UDP traffic to the Game
Node's `GAME_UDP_PORT` for voice and video media.
